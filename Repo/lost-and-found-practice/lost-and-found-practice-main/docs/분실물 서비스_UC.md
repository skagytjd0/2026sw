# 교내 분실물 서비스 Use Case Description

## 문서 기준

이 문서는 고객 요구사항과 SRS에 정의된 현재 범위의 유스케이스를 기술한다. 각 유스케이스는 사용자 목표를 달성하는 서비스 단위로 정의했다. 대괄호의 `[논의]`는 고객 또는 운영 책임자의 결정이 필요한 내용이며, 확정된 동작으로 간주하지 않는다.

| 참조 | 내용 |
|---|---|
| 고객 요구사항 | `NEEDS_1`~`NEEDS_7`, `SC1`~`SC8`, 공통 제약 `C_1` |
| SRS 기능 요구사항 | `FR_00`~`FR_06` |
| SRS 정책 | `Pol_00`~`Pol_07` |
| 공통 제약 | 가상 데이터를 사용하고 실제 개인정보와 학교 인증 연동은 제외한다. 개인 휴대전화 번호는 공개하지 않는다. |

## UC_01 분실물 찾기

| 항목 | 설명 |
|---|---|
| ID / 이름 | `UC_01` / 분실물 찾기 |
| 사용자와 목표 | **분실 학생**이 분실물 정보를 조회해 잃어버린 물품의 등록 여부, 보관 여부와 위치를 파악하고 불필요한 방문을 줄인다. |
| 관련 고객 요구·정책 ID | `NEEDS_1`, `NEEDS_6`, `SC1`, `C_1`; `FR_00`, `FR_01`; 공개 범위 관련 `Pol_00`~`Pol_03` |
| 사전조건 / 시작 사건 | 사전조건: 서비스에 조회 가능한 물품 정보가 존재할 수 있다. 로그인이나 학생 인증은 요구되지 않으며 학교 인증 연동은 제외한다. 시작 사건: 분실 학생이 분실물 조회를 시작한다. |
| 기본 흐름 | 1. 학생이 분실물 조회 화면을 연다.<br>2. 학생이 제공되는 조회 방법으로 물품을 찾는다. **[논의] 조회 조건(예: 물품 종류, 습득 장소, 날짜)은 미정이다.**<br>3. 서비스가 공개 가능한 조회 결과를 표시한다.<br>4. 학생이 해당 물품을 선택한다.<br>5. 서비스가 물품의 보관 여부와 위치를 표시한다.<br>6. 학생이 방문 또는 후속 문의 여부를 판단한다. |
| 대안·예외 흐름 | **분기 2 → 검색 조건을 입력하지 않음 →** [논의] 서비스가 전체 공개 목록을 보여줄지, 조건 입력을 요구할지 결정한다 → 허용 시 3단계로 복귀, 미허용 시 조회 종료.<br><br>**분기 3 → 일치하는 결과가 없음 →** 서비스가 결과가 없음을 알린다. [논의] 이때 담당 부서 문의 방법을 함께 안내할지 결정한다 → 안내하면 `UC_02`로 확장, 안내하지 않으면 조회 종료.<br><br>**분기 4 → 비슷한 결과가 여러 개임 →** [논의] 결과 구분에 필요한 공개 항목과 추가 선택 방법을 결정한다 → 학생이 하나를 선택하면 5단계로 복귀, 선택할 수 없으면 결과 목록에 머물거나 종료.<br><br>**분기 5 → 선택한 물품이 이미 인도 완료임 →** 서비스는 보관 상태를 표시한다. [논의] 인도 완료 물품의 위치 및 상세 정보도 공개할지 정한다 → 허용된 정보 표시 후 6단계로 복귀. |
| 사후조건: 성공 / 실패·취소 시 결과와 보존 조건 | 성공: 학생이 조회 결과에서 보관 여부와 위치를 확인한다. 조회만으로 물품 데이터가 변경되지는 않는다. 실패: 조회 결과가 없거나 조회 오류가 발생해도 물품 데이터는 변경되지 않는다. 취소: 학생이 조회를 중단해도 입력·등록 데이터는 변경되지 않는다. [논의] 검색어·조회 이력을 저장할지와 보존 기간은 미정이며, 실제 개인정보는 사용하지 않는다(`C_1`, `Pol_01`). |
| 미확정 사항·고객 질문 | [논의] 어떤 조회 조건과 공개 항목이 필요한가요? 인도 완료 물품을 검색 결과에 포함하나요? 검색 결과 없음·다수 결과·오류 상황에서 어떤 안내를 제공하나요? 조회 이력을 저장해야 하나요? |

## UC_02 담당 부서 문의 방법 확인하기

| 항목 | 설명 |
|---|---|
| ID / 이름 | `UC_02` / 담당 부서 문의 방법 확인하기 |
| 사용자와 목표 | **분실 학생**이 담당 부서의 공식 문의 경로를 확인해 조회만으로 해결되지 않은 상황을 이어서 처리한다. |
| 관련 고객 요구·정책 ID | `NEEDS_4`, `NEEDS_6`, `SC6`, `SC8`; `FR_02`; `Pol_03`, `Pol_07` |
| 사전조건 / 시작 사건 | 사전조건: 담당 부서와 문의 방법이 서비스에 설정되어 있을 수 있다. 시작 사건: 학생이 문의 방법 안내를 선택하거나 `UC_01`의 결과에서 문의 안내를 요청한다. |
| 기본 흐름 | 1. 학생이 문의 방법 안내를 요청한다.<br>2. 서비스가 확정된 담당 부서와 문의 경로를 표시한다.<br>3. 학생이 안내 내용을 확인하고 문의할 경로를 선택한다. |
| 대안·예외 흐름 | **분기 2 → 문의 정보가 등록되지 않음 →** 서비스는 안내 정보를 표시할 수 없다. [논의] 대체 안내(예: 학교 대표 안내 경로)를 제공할지 결정한다 → 대체 안내가 있으면 표시하고 종료, 없으면 정보 미제공 상태를 알리고 종료.<br><br>**분기 2 → 표시 정보에 개인 휴대전화 번호가 포함됨 →** 서비스는 개인 번호를 공개하지 않는다(`Pol_03`) → 공용 문의 정보가 있으면 그것을 표시하고 3단계로 복귀, 공용 정보가 없으면 안내 불가 메시지 후 종료. |
| 사후조건: 성공 / 실패·취소 시 결과와 보존 조건 | 성공: 학생이 담당 부서의 문의 방법을 확인한다. 실패: 문의 정보가 없거나 조회 오류가 발생해도 물품 데이터는 변경되지 않는다. 취소: 안내 화면을 닫아도 데이터 변경은 없다. [논의] 문의 경로 클릭 기록 또는 문의 내용 자체를 서비스가 저장할지는 미정이다. 개인 휴대전화 번호는 노출하지 않는다. |
| 미확정 사항·고객 질문 | [논의] 표시할 부서명, 공용 전화·이메일·방문 장소, 운영 시간은 무엇인가요? 문의 방법 안내를 모든 검색 결과에 표시할까요, 사용자가 선택할 때만 표시할까요? 문의 기능은 정보 안내만 제공하나요, 앱 내 문의 접수도 필요한가요? |

## UC_03 습득물 앱 등록하기

| 항목 | 설명 |
|---|---|
| ID / 이름 | `UC_03` / 습득물 앱 등록하기 |
| 사용자와 목표 | **습득 학생**이 습득한 물품을 앱으로 바로 등록해 분실 학생이 물품을 찾을 수 있게 한다. |
| 관련 고객 요구·정책 ID | `NEEDS_2`, `SC2`, `C_1`; `FR_03`; `Pol_00`~`Pol_02`, `Pol_05` |
| 사전조건 / 시작 사건 | 사전조건: 앱에서 물품 등록 기능에 접근할 수 있다. 학교 인증 연동은 제외한다. 로그인·인증 요구 여부는 미정이다. 시작 사건: 습득 학생이 앱에서 물품 등록을 선택한다. |
| 기본 흐름 | 1. 습득 학생이 앱의 물품 등록을 시작한다.<br>2. 서비스가 등록 항목과 안내를 표시한다.<br>3. 학생이 물품 정보를 입력한다.<br>4. 학생이 등록 내용을 제출한다.<br>5. 서비스가 입력 내용을 검증하고 물품 정보를 저장한다.<br>6. 서비스가 등록 완료를 알린다. |
| 대안·예외 흐름 | **분기 2 → 필수 입력 항목이 무엇인지** [논의] 고객 확인 후 등록 양식과 필수값을 정한다. 미확정 상태에서는 구체 필드를 단정하지 않는다.<br><br>**분기 4 → 필수 정보가 누락되거나 형식이 맞지 않음 →** 서비스가 오류 항목을 안내하고 입력값을 유지한다 → 3단계로 복귀.<br><br>**분기 4 → 학생이 제출 전에 취소함 →** 서비스는 등록을 저장하지 않는다. [논의] 작성 중 입력값을 임시 보존할지 결정한다 → 취소 종료.<br><br>**분기 5 → 중복 가능성이 있는 물품이 발견됨 →** [논의] 중복 판정 기준과 기존 등록 연결/신규 등록 선택 방식을 정한다 → 확인 후 저장하거나 등록 절차를 종료한다.<br><br>**분기 5 → 저장 오류 발생 →** 서비스가 실패를 알리고 재시도 방법을 제공한다 → 재시도 시 5단계로 복귀, 취소 시 종료. |
| 사후조건: 성공 / 실패·취소 시 결과와 보존 조건 | 성공: 제출된 물품 정보가 조회 가능한 등록 데이터로 저장된다. 실제 물품이 센터에 인계되었음을 의미하지는 않는다. [논의] 게시 전 담당자 승인이나 검토가 필요한지 미정이다. 실패: 검증 실패 시 등록 데이터는 생성되지 않고 입력값을 유지할지 여부는 정책 결정이 필요하다. 취소: 등록되지 않은 임시 입력값의 보존 여부는 미정이다. 실제 개인정보는 사용하지 않는다(`C_1`, `Pol_01`). |
| 미확정 사항·고객 질문 | [논의] 등록 필수 항목은 무엇인가요? 학생 인증 없이 등록을 허용하나요? 담당자 검토·승인이 필요한가요? 물품 보관 장소는 누가 관리하나요? 중복 등록은 어떻게 판정하나요? 작성 중 취소·오류 시 입력 내용을 보존할까요? 사진 등록은 현 범위에서 제외한다(`Pol_05`). |

## UC_04 센터 접수 물품 등록하기

| 항목 | 설명 |
|---|---|
| ID / 이름 | `UC_04` / 센터 접수 물품 등록하기 |
| 사용자와 목표 | **행정 담당자**가 분실물 센터에 접수된 습득 물품을 등록해 센터의 보관 관리와 학생 조회에 반영한다. |
| 관련 고객 요구·정책 ID | `NEEDS_2`, `SC2`; `FR_04`, `FR_06`; `Pol_00`~`Pol_02` |
| 사전조건 / 시작 사건 | 사전조건: 습득 물품이 분실물 센터에 접수되고 행정 담당자가 등록 기능을 사용할 수 있다. 시작 사건: 담당자가 접수 물품 등록을 시작한다. |
| 기본 흐름 | 1. 담당자가 센터 접수 물품 등록을 시작한다.<br>2. 서비스가 등록 양식을 표시한다.<br>3. 담당자가 물품 정보를 입력한다.<br>4. 담당자가 등록 내용을 확인하고 저장한다.<br>5. 서비스가 입력 내용을 검증하고 저장한다.<br>6. 서비스가 등록 완료를 알린다. |
| 대안·예외 흐름 | **분기 3 → 필수 항목·형식이 미정임 →** [논의] 행정 담당자가 확인할 등록 항목, 필수값 및 유효성 규칙을 운영 책임자가 확정해야 한다.<br><br>**분기 4 → 저장 전 내용 오류 발견 →** 담당자가 내용을 수정한다 → 3단계로 복귀.<br><br>**분기 4 → 담당자가 등록을 취소함 →** 서비스는 신규 물품 레코드를 만들지 않는다. [논의] 입력 중 내용의 임시 저장 여부를 정한다 → 취소 종료.<br><br>**분기 5 → 앱 등록 건과 중복 가능성이 있음 →** [논의] 기존 건에 병합할지 별도 접수 건으로 기록할지 중복 처리 규칙에 따라 결정한다 → 병합 또는 별도 저장 후 6단계로 진행, 판단 불가 시 보류 후 종료.<br><br>**분기 5 → 저장 오류 발생 →** 서비스가 오류를 알린다 → 재시도하면 5단계로 복귀, 취소하면 종료. |
| 사후조건: 성공 / 실패·취소 시 결과와 보존 조건 | 성공: 센터 접수 물품이 관리 및 조회 대상에 저장된다. 실패: 저장 실패 시 불완전한 물품 레코드가 생성되지 않아야 한다. [논의] 실패한 입력 내용을 보존할지 미정이다. 취소: 신규 레코드는 생성되지 않는다. [논의] 취소 시 임시 저장·감사 이력 여부를 정한다. 실제 개인정보는 사용하지 않는다(`C_1`, `Pol_01`). |
| 미확정 사항·고객 질문 | [논의] 센터 등록 필수 항목은 무엇인가요? 앱 등록 건과 중복 여부를 어떤 기준으로 확인하나요? 중복 건을 병합하거나 별도 관리할 권한은 누구에게 있나요? 저장 오류나 취소 시 입력 내용을 보존해야 하나요? |

## UC_05 등록된 물품 관리하기

| 항목 | 설명 |
|---|---|
| ID / 이름 | `UC_05` / 등록된 물품 관리하기 |
| 사용자와 목표 | **행정 담당자**가 등록된 물품 정보를 조회·관리해 실제 보관 업무와 서비스 조회 정보가 일치하도록 한다. |

## UC_06 물품 인도 상태 처리하기

| 항목 | 설명 |
|---|---|
| ID / 이름 | `UC_06` / 물품 인도 상태 처리하기 |
| 사용자와 목표 | **행정 담당자**가 실제 인도 결과를 기록해 인도 완료 물품과 보관 중 물품을 구분하고, 학생에게 현재 상태를 제공한다. |
| 관련 고객 요구·정책 ID | `NEEDS_3`, `SC3`; `FR_05`; `Pol_04` |
| 사전조건 / 시작 사건 | 사전조건: 물품이 서비스에 등록되어 있고 행정 담당자가 상태 변경 권한을 가진다. 시작 사건: 물품을 학생에게 인도했거나 상태를 정정할 필요가 생긴다. |
| 기본 흐름 | 1. 담당자가 대상 물품을 조회한다.<br>2. 담당자가 현재 상태를 확인한다.<br>3. 담당자가 인도 완료 처리를 선택한다.<br>4. 서비스가 변경 내용을 확인하도록 표시한다.<br>5. 담당자가 확정한다.<br>6. 서비스가 상태를 저장하고 조회 화면에 반영한다.<br>7. 서비스가 완료 결과를 알린다. |
| 대안·예외 흐름 | **분기 2 → 물품이 이미 인도 완료 상태임 →** 서비스가 현재 상태를 알린다 → 변경 없이 종료.<br><br>**분기 3 → 실제 인도 여부가 확인되지 않음 →** [논의] 인도 확인 기준(담당자 확인, 수령 확인 등)을 정한다 → 확인되면 4단계로 진행, 확인되지 않으면 상태 변경을 보류하고 종료.<br><br>**분기 5 → 담당자가 취소함 →** 상태를 변경하지 않는다 → 취소 종료.<br><br>**분기 6 → 저장 실패 또는 상태 충돌 발생 →** 서비스가 변경 실패를 알리고 기존 상태를 유지한다 → 재조회 후 재시도하면 1단계로 복귀, 취소하면 종료.<br><br>**분기 6 → 잘못된 인도 완료 상태를 정정해야 함 →** [논의] 정정 권한, 사유 입력, 이전 상태 복구 및 이력 보존 방식을 정한다 → 허용된 경우 정정 절차를 수행하고 6단계로 복귀, 권한이 없으면 종료. |
| 사후조건: 성공 / 실패·취소 시 결과와 보존 조건 | 성공: 상태가 인도 완료로 변경되고 조회 결과에 반영된다(`Pol_04`). 실패: 저장 실패·충돌 시 기존 상태를 유지한다. 취소: 상태를 변경하지 않는다. [논의] 성공·정정 작업의 작업자, 시각, 이전/이후 상태 및 사유를 기록할지와 보존 기간을 정한다. |
| 미확정 사항·고객 질문 | [논의] 인도 완료 처리의 기준과 확인 증빙은 무엇인가요? 상태 정정은 누가 할 수 있나요? 정정 사유를 받아야 하나요? 상태 변경 이력은 어떤 항목을 얼마 동안 보존하나요? 변경 후 조회 반영 목표(현재 SRS 제안 5초)는 적절한가요? |
